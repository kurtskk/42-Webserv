// O que este módulo faz e por que existe

O módulo Config é o primeiro a rodar no servidor — antes de qualquer socket, qualquer conexão. Ele lê o arquivo de texto webserv.conf e transforma esse texto em objetos C++ que o resto do servidor usa para tomar decisões.

Resultado final: um std::vector<ServerConfig> onde cada ServerConfig contém uma porta, um server_name, regras de erro e um vetor de LocationConfig com as rotas. Tudo isso é passado para o WebServ que lê essas estruturas durante toda a vida do servidor.

O módulo tem 3 classes: Config (lê e valida o arquivo), ServerConfig (representa um bloco server {}), LocationConfig (representa um bloco location {}).

01 Config::load() — ponto de entrada do módulo Config.cpp
void Config::load(const std::string &filename)
Recebe de quem / quando
Chamada diretamente pelo main() logo depois de criar o objeto Config: config.load(argv[1]). Recebe o caminho do arquivo de configuração como string. É a única função pública de leitura do módulo — todo o resto é privado.
O que faz — passo a passo
1. Abre o arquivo com std::ifstream. Se falhar → lança std::runtime_error. Esse erro é capturado pelo try/catch no main().

2. Lê linha por linha com std::getline. Para cada linha: remove comentários (stripComment), quebra em tokens (tokenize), ignora linhas vazias.

3. Espera encontrar exatamente server { como dois tokens. Se encontrar → chama parseServerBlock() que consome as linhas seguintes até o } correspondente e preenche um ServerConfig. Empurra o ServerConfig preenchido para servers.

4. Se encontrar qualquer coisa que não seja server { no nível raiz → lança exceção. Não há flexibilidade — o formato é exato.
O que retorna / para quem
Retorna void. O resultado fica em servers (atributo privado). O main() acessa via config.getServers() — que retorna const std::vector<ServerConfig> & — e passa para o construtor do WebServ.
Config.cpp — Config::load()
std::ifstream file(filename.c_str());  // c_str() porque é C++98 — ifstream não aceita std::string diretamente
if (!file.is_open())
    throw std::runtime_error("Could not open config file: " + filename);

std::string line;
while (std::getline(file, line)) {     // lê linha por linha até EOF
    stripComment(line);               // remove tudo após '#'
    std::vector<std::string> tokens = tokenize(line);
    if (tokens.empty()) continue;   // linha em branco ou só comentário
    if (tokens[0] == "server" && tokens.size() == 2 && tokens[1] == "{") {
        ServerConfig server;             // criado na stack, copiado depois
        parseServerBlock(file, server); // consome linhas até o '}' do server
        servers.push_back(server);
    }
    else
        throw std::runtime_error("Invalid config file format...");
}
std::ifstream file(filename.c_str()) — em C++98, o construtor de ifstream aceita apenas const char*, não std::string. Por isso o .c_str() que converte a string para ponteiro C. Em C++11 isso seria desnecessário.
std::getline(file, line) — retorna uma referência ao stream. Em contexto booleano (dentro do while), o stream é convertido para bool: true se a leitura funcionou, false se chegou ao EOF ou ocorreu erro. É o idioma padrão C++ para ler linha por linha.
O arquivo é lido linha por linha em vez de carregado inteiro na memória porque o arquivo de configuração pode ser grande. Também porque processar linha por linha permite detectar erros de formato exatamente onde ocorrem — sabemos em qual linha o problema está.
void Config::stripComment(std::string &line)
O que faz
Encontra o primeiro # na linha e apaga tudo a partir daí com erase(pos). Modifica a string in-place (por referência).
Config.cpp — stripComment()
size_t pos = line.find('#');
if (pos != std::string::npos)   // npos = "não encontrado" = maior size_t possível
    line.erase(pos);              // erase(pos) sem segundo arg apaga até o fim
std::string::npos é uma constante estática do tipo size_t com valor máximo (normalmente -1 em aritmética sem sinal, que é o maior valor possível). find() retorna npos quando não encontra. erase(pos) sem segundo argumento apaga da posição pos até o fim — equivalente a erase(pos, string::npos).
Passagem por referência (std::string &) evita copiar a string. A função modifica diretamente o objeto que foi passado. Se fosse const std::string & não poderia modificar — sem o const, pode.
std::vector<std::string> Config::tokenize(const std::string &line)
O que faz
Quebra a linha em palavras separadas por qualquer whitespace (espaço, tab, múltiplos espaços). Retorna um vector<string> com as palavras.
Config.cpp — tokenize()
std::vector<std::string> tokens;
std::string token;
std::istringstream tokenStream(line);   // trata a string como um stream
while (tokenStream >> token) {           // >> pula whitespace, lê até próximo whitespace
    tokens.push_back(token);
}
return (tokens);
std::istringstream é um stream que lê de uma string em vez de um arquivo. O operador >> num stream de string funciona igual ao cin >>: pula whitespace no início, lê até o próximo whitespace. Isso faz com que múltiplos espaços/tabs entre tokens sejam tratados como um único separador automaticamente.
Resultado para a linha " location /uploads/ { ": tokens[0]="location", tokens[1]="/uploads/", tokens[2]="{". Espaços extras e tabs são ignorados automaticamente.
Usar istringstream + >> é o idioma mais idiomático em C++ para split por whitespace. A alternativa seria iterar caractere por caractere — muito mais verboso. A desvantagem é que não preserva ordem de múltiplas palavras em valores (mas nenhum valor no conf precisa disso).
02 Config::parseServerBlock() — lê um bloco server {} Config.cpp
void Config::parseServerBlock(std::ifstream &file, ServerConfig &server)
Recebe de quem
Chamada por load() quando encontra server {. Recebe o mesmo ifstream que o load está usando — o cursor de leitura do arquivo já está na linha após o server {. Recebe também uma referência para o ServerConfig que deve preencher.
Por que o ifstream é passado por referência
O ifstream representa a posição atual de leitura no arquivo. Se fosse passado por cópia, a função leria do início do arquivo. Passando por referência, parseServerBlock continua do ponto onde load() parou — esse é o mecanismo que permite parsear blocos aninhados sequencialmente.
Como funciona — o loop de leitura
Mesmo padrão de load(): getline → stripComment → tokenize → testa o primeiro token. A diferença: quando encontra } faz return imediatamente. Quando encontra location /path {, cria um LocationConfig(tokens[1]), chama parseLocationBlock(file, location) — passando o mesmo stream — e depois faz server.addLocation(location).
E se o bloco não fechar?
O while(getline) termina quando chega no EOF sem ter encontrado o }. Depois do while há sempre um throw runtime_error("Server block not closed properly"). O return só acontece dentro do loop quando encontra o } — o throw após o loop é o tratamento de erro de bloco não fechado.
Config.cpp — parseServerBlock() — estrutura principal
while (std::getline(file, line)) {
    // ... stripComment, tokenize, skip empty ...

    if (tokens[0] == "}")
        return;                          // fim do bloco server — retorno normal

    else if (tokens[0] == "listen" && tokens.size() == 2) {
        int port = parsePort(tokens[1]);   // valida e converte
        server.setListenPort(port);
    }
    else if (tokens[0] == "location" && tokens.size() == 3 && tokens[2] == "{") {
        LocationConfig location(tokens[1]); // tokens[1] = o path "/uploads/"
        parseLocationBlock(file, location); // passa o MESMO stream
        server.addLocation(location);      // cópia do LocationConfig vai para o vector
    }
    // ... outros campos: server_name, root, index, error_page, client_max_body_size ...
}
throw std::runtime_error("Server block not closed properly"); // só chega aqui se EOF sem '}'
Ordem de verificação dos tokens: sempre checa tokens[0] (a diretiva) e tokens.size() (número de argumentos) juntos. Ex: tokens[0] == "listen" && tokens.size() == 2 garante que existe exatamente um argumento após o listen. Se tiver mais ou menos tokens, a linha é ignorada silenciosamente (cai no else implícito — não há tratamento de campo desconhecido).
Fluxo do cursor do arquivo durante o parse de dois servers:
load() lê "server {" → chama parseServerBlock(file) → parseServerBlock lê linhas do servidor 1 → encontra "}" → retorna → load() volta ao while → lê "server {" do servidor 2 → chama parseServerBlock novamente → e assim por diante.
03 Config::parseLocationBlock() — lê um bloco location {} Config.cpp
void Config::parseLocationBlock(std::ifstream &file, LocationConfig &location)
Estrutura idêntica ao parseServerBlock
Mesmo padrão: loop getline, stripComment, tokenize. Retorna quando encontra }. Lança exceção se chega ao EOF sem fechar. A diferença é o conjunto de diretivas que reconhece — são as diretivas de location: root, index, autoindex, allow_methods, cgi_ext, cgi_path, client_max_body_size, upload_store, return.
Diretiva allow_methods — múltiplos valores
É a única diretiva com número variável de tokens. Em vez de checar tokens.size() == N, itera a partir do índice 1 e chama location.addAllowedMethod(tokens[i]) para cada token. Isso permite allow_methods GET POST DELETE ou só allow_methods GET.
Diretiva return — o redirect
A mais complexa: return 302 https://www.google.com. O código é lido como string (tokens[1]) e convertido para int via istringstream. A lógica usa o truque iss >> code + iss.get(extra) para garantir que a string é um número puro — sem letras após os dígitos.
Config.cpp — parseLocationBlock() — trecho allow_methods e return
// allow_methods aceita 1 ou mais métodos
else if (tokens[0] == "allow_methods") {
    for (size_t i = 1; i < tokens.size(); ++i)
        location.addAllowedMethod(tokens[i]);
}

// return 302 https://... — parse do código numérico
else if (tokens[0] == "return" && tokens.size() == 3) {
    std::istringstream issCode(tokens[1]);
    int code;
    char extra;
    if (!(issCode >> code) || issCode.get(extra))  // ver explicação abaixo
        throw std::runtime_error("Invalid redirect code: '" + tokens[1] + "'");
    location.setRedirectCode(code);
    location.setRedirectUrl(tokens[2]);
}
O padrão iss >> code + iss.get(extra):

iss >> code — tenta ler um int. Se a string começa com letras ou está vazia, falha → a condição !(iss >> code) é true → lança exceção. Isso detecta "abc", "", "3x2" parcialmente — mas "3x2" seria lido como 3 com sucesso aqui.

iss.get(extra) — tenta ler mais um caractere após o número. Se conseguir (retorna true), significa que havia algo após os dígitos — "302abc" seria inválido. Se não conseguir (stream no EOF), a string era um número puro. A condição || iss.get(extra) captura esse caso.
Este padrão de validação (iss >> val + iss.get(extra)) aparece em três lugares no módulo: parsePort, parseErrorCode e aqui no return. É o idioma padrão C++98 para "converta e garanta que a string inteira é um número".
04 Funções Helper de Parse e Validação Config.cpp — funções estáticas e privadas
static int Config::parsePort(const std::string &value)
O que valida
Converte string para int, verifica que não há caracteres extras (padrão iss+get(extra)), e verifica que está no range 1–65535. TCP tem portas de 0 a 65535 — porta 0 é reservada para o sistema.
Config.cpp — parsePort()
std::istringstream iss(value);
int port;
char extra;
if (!(iss >> port) || iss.get(extra))          // não é número puro
    throw std::runtime_error("Invalid port: '" + value + "' is not a valid number");
if (port < 1 || port > 65535)                  // range TCP válido
    throw std::runtime_error("Invalid port: " + value + " out of range (1-65535)");
return (port);
É static porque não precisa acessar atributos da instância — opera só sobre o argumento. Em C++, funções membro estáticas não recebem o ponteiro this implicitamente. Isso também permite chamá-la sem um objeto: Config::parsePort("8080").
static size_t Config::parseBodySize(const std::string &value)
O que faz — suporte a sufixos K/M/G/T
Aceita valores como 100, 200M, 1G. Itera manualmente sobre os caracteres para separar a parte numérica da parte de sufixo — porque istringstream pararia nos dígitos sem consumir o sufixo.
Config.cpp — parseBodySize() — algoritmo
size_t i = 0;
while (i < value.length() && std::isdigit(value[i]))
    i++;                              // avança enquanto for dígito

std::string numStr = value.substr(0, i);   // parte numérica: "200"
std::string suffix = value.substr(i);     // sufixo: "M" ou ""

// suffix não pode ter mais de 1 caractere
if (suffix.length() > 1)
    throw std::runtime_error("Invalid body size: invalid suffix");

// converte parte numérica
std::istringstream issNum(numStr);
unsigned long num;
if (!(issNum >> num)) throw ...;

// aplica multiplicador via switch
size_t multiplier = 1;
switch (suffix[0]) {
    case 'k': case 'K': multiplier = 1024; break;
    case 'm': case 'M': multiplier = 1024 * 1024; break;
    case 'g': case 'G': multiplier = 1024 * 1024 * 1024; break;
    case 't': case 'T': multiplier = static_cast<size_t>(1024UL*1024*1024*1024); break;
    default: throw ...;
}
return (static_cast<size_t>(num) * multiplier);
static_cast<size_t>(1024UL * 1024 * 1024 * 1024) — o sufixo UL em 1024UL força o literal para unsigned long. Sem isso, 1024 * 1024 * 1024 * 1024 seria calculado em int de 32 bits e daria overflow (o valor é 1TB = 2⁴⁰). Com UL, a aritmética ocorre em unsigned long (64 bits em sistemas modernos). O static_cast<size_t> converte para o tipo de retorno sem warning.
switch com case 'k': case 'K': — dois cases consecutivos sem break entre eles fazem fall-through intencional: ambos executam o mesmo código (multiplier = 1024; break;). É a forma idiomática C de "aceitar maiúscula ou minúscula".
Por que o parser não valida unicidade de porta
O que o parser permite e por quê
O Config não impõe nenhuma restrição sobre o número de porta em parseServerBlock — qualquer quantidade de blocos server {} pode declarar o mesmo listen. Isso é deliberado: é o que torna possível configurar virtual hosting por nome, onde duas ou mais server {} compartilham a mesma porta e são diferenciadas apenas pelo server_name contra o header Host da requisição. A unicidade real — um socket por porta — já é garantida pelo próprio bind() do sistema operacional; replicar essa checagem no parser, sem ele ter como distinguir "mesma porta, mesmo nome" de "mesma porta, nome diferente", seria decidir cedo demais com informação de menos.
Config.cpp — parseServerBlock(), trecho do listen
else if (tokens[0] == "listen" && tokens.size() == 2) {
    int port = parsePort(tokens[1]);
    server.setListenPort(port);
}
O que acontece quando duas configs pedem a mesma porta sem nenhuma diferenciação possível
Em WebServ::setupServers(), cada ServerConfig tenta abrir seu próprio socket de listen dentro de um try/catch independente. Se duas configs pedem exatamente a mesma porta sem nenhuma forma de diferenciação, o segundo bind() falha com EADDRINUSE, o erro é capturado e logado, e o programa segue rodando normalmente nas portas que conseguiram abrir — sem crashar.
O que faz a porta compartilhada funcionar de fato na prática: WebServ::getServerForRequest(req, serverFd) traduz o serverFd (o socket de listen por onde aquele cliente entrou) na porta real via serverSockets, filtra só os ServerConfig que escutam naquela porta, e dentro desse subconjunto escolhe pelo Host/server_name — com fallback pro primeiro server daquela porta se nenhum nome bater. Vale revisar o módulo do WebServ pra ver essa função com detalhe.
05 ServerConfig — a estrutura de dados de um servidor ServerConfig.hpp / ServerConfig.cpp
class ServerConfig
Atributos e valores padrão
O construtor padrão inicializa todos os atributos na lista de inicialização. Isso é importante em C++ — atributos não inicializados têm valores indeterminados (lixo de memória).
ServerConfig.cpp — construtor com lista de inicialização
ServerConfig::ServerConfig() :
    listenPort(8080),         // porta padrão se não configurado
    serverName(""),           // sem nome padrão
    clientMaxBodySize(1048576), // 1MB padrão = 1024 * 1024
    root(""), index("")
    {}
Lista de inicialização do construtor (: attr(val), ...) — inicializa os atributos antes do corpo do construtor executar. Para tipos primitivos (int, size_t) é equivalente a uma atribuição no corpo. Para tipos classe (std::string, std::vector) é mais eficiente — evita a construção padrão seguida de atribuição. Em C++, sempre prefira lista de inicialização.
Copy constructor e operator=
Ambos implementados explicitamente. O copy constructor chama o operator= para evitar duplicar a lógica: *this = other. O operator= copia todos os atributos um a um com o guard if (this != &other).
ServerConfig.cpp — operator=
ServerConfig &ServerConfig::operator=(const ServerConfig &other) {
    if (this != &other) {          // auto-atribuição: s = s — evita se-destruir antes de copiar
        listenPort = other.listenPort;
        serverName = other.serverName;
        errorPages = other.errorPages; // std::map faz cópia profunda automaticamente
        clientMaxBodySize = other.clientMaxBodySize;
        root = other.root;
        index = other.index;
        locations = other.locations; // vector faz cópia profunda automaticamente
    }
    return (*this);               // retorna referência para permitir s1 = s2 = s3
}
Rule of Three em C++98: se você define qualquer um dos três — destrutor, copy constructor, operator= — você provavelmente precisa dos três. Aqui todos são definidos porque ServerConfig contém um vector<LocationConfig>. Se o compilador gerasse o copy constructor padrão, ele faria cópia membro a membro — o que funcionaria nesse caso, pois vector já tem seu próprio copy correto. Mas a implementação explícita documenta a intenção.
Por que return (*this) em operator=? — o operator= retorna referência para o próprio objeto. Isso permite encadeamento: a = b = c funciona porque b = c retorna b, que é então atribuído a a. Os parênteses em (*this) são estilo — semanticamente equivalente a return *this.
O atributo errorPages — map<int, string>
Mapeia código de erro HTTP (ex: 404) para caminho do arquivo de página de erro (ex: "/404.html"). O addErrorPage simplesmente faz errorPages[code] = path — se o mesmo código aparecer duas vezes no conf, o segundo sobrescreve o primeiro (comportamento do map em inserção com chave existente).

06 LocationConfig — a estrutura de dados de uma rota LocationConfig.hpp / LocationConfig.cpp
class LocationConfig
Dois construtores
Tem um construtor padrão (sem args) e um construtor que recebe o path da location. O path é definido uma única vez na construção — não há setter para ele. Isso é intencional: o path identifica a location e não deve mudar depois.
LocationConfig.cpp — construtores
// Construtor padrão — path vazio
LocationConfig::LocationConfig() :
    path(""), root(""), index(""), autoindex(false),
    cgiExtension(""), cgiPath(""), clientMaxBodySize(0),
    uploadStore(""), redirectCode(0), redirectUrl("")
    {}

// Construtor com path — usado em parseServerBlock
// LocationConfig location(tokens[1]) onde tokens[1] = "/uploads/"
LocationConfig::LocationConfig(const std::string &locationPath) :
    path(locationPath),   // só isso muda em relação ao padrão
    root(""), ...
    {}
clientMaxBodySize começa em 0 (não em 1MB como no ServerConfig). Isso é intencional: 0 significa "não configurado nesta location — use o valor do servidor". Em HttpResponse::generateResponse() a lógica é: maxBody = location.clientMaxBodySize > 0 ? location.clientMaxBodySize : server.clientMaxBodySize.
allowedMethods — vector<string> e addAllowedMethod
addAllowedMethod(method) simplesmente faz allowedMethods.push_back(method). Não valida se o método é um string HTTP válido — aceita qualquer coisa. A validação acontece depois, em HttpResponse, quando compara o método da requisição com o vetor. Separação de responsabilidades: Config não sabe o que é um método HTTP válido, só armazena o que foi configurado.

Quem usa esse resultado depois: o WebServ guarda uma referência Config &config. Em setupServers() itera sobre config.getServers() para criar um socket de listen por porta. Em getServerForRequest(req, serverFd), primeiro filtra os ServerConfig que escutam na porta real por onde aquele cliente entrou (via serverFd → serverSockets), e só dentro desse subconjunto desempata pelo header Host contra server_name. Em handleClientRead(), passa o ServerConfig correto para HttpResponse::generateResponse() que usa as locations para rotear a requisição.
O módulo Config não persiste depois do startup — os objetos ServerConfig e LocationConfig ficam vivos durante toda a execução do servidor porque WebServ guarda referência ao Config que por sua vez mantém o vector<ServerConfig> em memória. Modificar o conf em disco enquanto o servidor está rodando não tem efeito — seria necessário reiniciar.
