// O que este módulo faz e quem são suas 3 classes

SocketUtils — helper estático puro. Duas funções: cria um socket TCP de escuta (createListeningSocket) e seta um fd como não-bloqueante (setNonBlocking). Não guarda estado, não pode ser instanciada — todos os construtores são privados.

Client — representa uma conexão TCP aberta com um cliente. Acumula o texto cru da requisição num buffer, gerencia os dois modos de resposta (buffer em memória ou arquivo em disco), e carrega todo o estado do CGI associado a essa conexão.

WebServ — o motor do servidor. Dono único do array pollfds e do loop poll(). Aceita conexões, despacha leitura e escrita de clientes, orquestra o CGI assíncrono (fork → body em arquivo → read stdout → finishCgi) e limpa recursos via removeClient().

Hierarquia de dependência: SocketUtils não depende de ninguém. Client não depende de ninguém. WebServ depende de todos — Config, Client, SocketUtils, HttpRequest, HttpResponse, CgiHandler.

01 SocketUtils — criação de sockets e non-blocking SocketUtils.cpp / SocketUtils.hpp
static int SocketUtils::createListeningSocket(int port)
Sequência de syscalls e por que cada uma existe
1. socket(AF_INET, SOCK_STREAM, 0) — cria um socket TCP IPv4. AF_INET = IPv4, SOCK_STREAM = TCP (orientado a conexão, confiável, com garantia de ordem). Retorna um fd como qualquer outro arquivo.

2. setsockopt(SO_REUSEADDR) — permite reutilizar a porta imediatamente após o servidor reiniciar. Sem isso, o kernel mantém a porta em estado TIME_WAIT por 2 minutos após fechar — o bind() falharia. É obrigatório em qualquer servidor que pode ser reiniciado.

3. setsockopt(SO_RCVBUF / SO_SNDBUF, 1MB) — aumenta o buffer de kernel para recv e send para 1MB. O padrão é ~128KB. Para transferências grandes (uploads, arquivos) isso reduz o número de syscalls necessárias. São avisos (warning) se falharem — não interrompem o setup.

4. bind() — associa o socket à porta configurada em todas as interfaces (INADDR_ANY). O endereço precisa ser preenchido numa struct sockaddr_in zerada com memset. htons(port) converte a porta para network byte order (big-endian).

5. listen(SOMAXCONN) — ativa o socket para aceitar conexões. SOMAXCONN é a constante do sistema para o backlog máximo (fila de conexões pendentes aguardando accept()) — tipicamente 128.

6. setNonBlocking(fd) — seta O_NONBLOCK. Feito por último para que as operações de setup (bind, listen) sejam síncronas e retornem erros claros.
SocketUtils.cpp — createListeningSocket()
int listenFd = socket(AF_INET, SOCK_STREAM, 0);
if (listenFd < 0) throw ...;

int opt = 1;
setsockopt(listenFd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));

int bufferSize = 1024 * 1024;
setsockopt(listenFd, SOL_SOCKET, SO_RCVBUF, &bufferSize, sizeof(bufferSize));
setsockopt(listenFd, SOL_SOCKET, SO_SNDBUF, &bufferSize, sizeof(bufferSize));

struct sockaddr_in serverAddr;
std::memset(&serverAddr, 0, sizeof(serverAddr));
serverAddr.sin_family      = AF_INET;
serverAddr.sin_addr.s_addr = INADDR_ANY;   // todas as interfaces de rede
serverAddr.sin_port        = htons(port); // host → network byte order

bind(listenFd, reinterpret_cast<struct sockaddr*>(&serverAddr), sizeof(serverAddr));
listen(listenFd, SOMAXCONN);
setNonBlocking(listenFd);
return (listenFd);
reinterpret_cast<struct sockaddr*>(&serverAddr) — bind() aceita struct sockaddr* genérico, mas preenchemos um struct sockaddr_in (específico para IPv4). O cast diz ao compilador: "trate este ponteiro como se fosse do outro tipo". É a abordagem padrão POSIX para polimorfismo de estruturas em C. Em C seria um cast implícito; em C++ o reinterpret_cast é explícito e deixa claro que é um cast perigoso (o programador sabe o que está fazendo).
htons(port) — "host to network short". Converte um short (16 bits) do byte order do host (little-endian em x86) para network byte order (big-endian, definido pelo RFC). Necessário porque redes TCP/IP usam big-endian. O inverso é ntohs(). Para 32 bits (endereço IP): htonl() / ntohl().
static void SocketUtils::setNonBlocking(int fd)
Como funciona — F_GETFL + F_SETFL
Usa duas chamadas fcntl(). Primeiro F_GETFL obtém as flags atuais do fd (pode haver outras flags já setadas — não queremos apagá-las). Depois F_SETFL com flags | O_NONBLOCK acrescenta o bit de non-blocking sem afetar as flags existentes. O operador | (OR bit a bit) seta o bit específico sem tocar nos outros.
SocketUtils.cpp — setNonBlocking()
int flags = fcntl(fd, F_GETFL, 0);     // obtém flags atuais
if (flags == -1) throw ...;
if (fcntl(fd, F_SETFL, flags | O_NONBLOCK) == -1) throw ...; // seta bit NONBLOCK
Com O_NONBLOCK, operações como recv() e send() retornam imediatamente com EAGAIN/EWOULDBLOCK quando não há dados disponíveis, em vez de bloquear o processo. Isso é essencial para que um único processo possa gerenciar centenas de conexões simultâneas sem que uma conexão lenta trave todas as outras.
Por que SocketUtils não pode ser instanciada? O construtor padrão, copy constructor, operator= e destrutor são todos privados. A classe é uma coleção de funções estáticas utilitárias — um "namespace com restrições". Instanciar não faria sentido pois não guarda estado. Este padrão é chamado de "utility class".
02 Client — construtor e destrutor Client.cpp / Client.hpp
Client(int f, int s)
A lista de inicialização — todos os 18 atributos
Todos os atributos são inicializados na lista de inicialização antes do corpo do construtor. Isso é obrigatório em C++ para garantir valores determinísticos — atributos não inicializados têm valores lixo. O corpo do construtor faz apenas memset(cgiTmpPath, 0, sizeof(cgiTmpPath)) — zerando o array de chars que não pode ser inicializado diretamente na lista.
Client.cpp — construtor
Client::Client(int f, int s) :

    cgiTotalOutput(0),
    cgiStartTime(0),
    fd(f),             // fd do socket do cliente

    responseFileStartOffset(0),
    responseSendOffset(0),
    responseHeaderSize(0),
    cacheOffset(0),
    requestComplete(false),
    responseComplete(false),

    needs100Continue(false),

Por que -1 para fds? Fds válidos são sempre >= 0. Usar -1 como sentinela é o padrão POSIX — permite checar if (cgiPipeIn >= 0) antes de fechar ou usar. Isso evita double-close (fechar um fd já fechado — comportamento indefinido que pode fechar outro fd aberto com o mesmo número).
serverFd guarda qual socket de listen aceitou essa conexão. É usado em WebServ::getServerForRequest() para identificar qual ServerConfig corresponde — quando dois servidores têm o mesmo server_name mas portas diferentes, a porta do socket de origem determina o servidor correto.
Client::~Client()
Responsabilidades do destrutor — RAII
O destrutor do Client é o ponto central de liberação de recursos. Implementa o princípio RAII.
Client.cpp — ~Client()
if (responseFileFd >= 0)
    close(responseFileFd);                  // fecha arquivo estático ou tmp do CGI
if (!responseFilePath.empty() && deleteFileOnClose)
    std::remove(responseFilePath.c_str());   // deleta arquivo tmp do CGI (std::remove)
if (cgiPipeOut >= 0) close(cgiPipeOut);
if (cgiTmpFd >= 0)   close(cgiTmpFd);     // fecha fd do arquivo tmp
if (cgiTmpPath[0])                           // [0] != '\0' → path foi preenchido
    std::remove(cgiTmpPath);               // deleta arquivo tmp se ainda existir
O destrutor tem dois caminhos para deletar o arquivo temporário do CGI: responseFilePath + deleteFileOnClose (para o caso em que setFileResponse() foi chamado com o tmp) e cgiTmpPath (para o caso em que o CGI estava rodando mas nunca chegou ao finishCgi()). Em ambos os casos usa std::remove() — equivalente ao unlink() POSIX. Isso garante que nenhum arquivo temporário fica para trás.
03 Client — acumulação do buffer de requisição Client.cpp
void Client::appendRequest(const char *buffer, ssize_t bytes)
O que faz
Chama requestBuffer.append(buffer, bytes). Esse método de std::string adiciona exatamente bytes caracteres do buffer ao final da string — correto para dados binários que podem conter \0. O requestBuffer acumula todos os dados de uma requisição que pode chegar fragmentada em múltiplos recv().
TCP é um protocolo de stream — não preserva fronteiras de mensagem. Uma requisição HTTP de 5KB pode chegar em 3 recv(): 2KB, 2KB, 1KB. Por isso acumulamos em buffer e só processamos quando isRequestComplete() confirma que temos tudo.
04 Client — os dois modos de resposta Client.cpp
void Client::setResponse(const std::string &response)
Modo buffer — toda a resposta em memória
Copia a string completa (header + body) para responseBuffer. Zera todos os offsets. Seta fileBasedResponse = false. Usado para: respostas de erro, respostas curtas (autoindex, POST, DELETE), 100-Continue, respostas de sessão.
05 Client — isRequestComplete() e isCgiTimedOut() Client.cpp
bool Client::isRequestComplete()
Fase 1 — parse de headers
A flag headersParsed garante que a fase de parse de headers roda apenas na primeira chamada em que os headers chegaram completos.
Fase 2 — verificação de completude do body
Três casos após os headers estarem parsados:
a) Content-Length declarado: espera requestBuffer.length() >= headerEnd + 4 + contentLength. O +4 é para os 4 bytes do \r\n\r\n.
b) Transfer-Encoding: chunked: espera que o buffer termine com "0\r\n\r\n".
c) Nenhum dos dois: requisição sem body — completa assim que os headers chegaram.
06 WebServ — setupServers() e run() WebServ.cpp
void WebServ::run()
Estrutura do loop — duas fases por iteração
Fase 1 — Timeout de CGI: antes de chamar poll(), itera sobre todos os clients e checa isCgiTimedOut(). Se timed out: mata o processo com kill(SIGKILL), recolhe com waitpid(status, 0) bloqueante, prepara resposta 504, limpa pipes e referências no cgiPipeToClient.

Fase 2 — Processar revents: a chamada poll(&pollfds[0], pollfds.size(), 1000) bloqueia até 1 segundo. Itera sobre os fds prontos. Categoriza: serverSocket (accept), cgiPipe (cgiRead), clienteFd (clientRead, clientWrite ou erro). Após cada handler: break.
07 WebServ — acceptNewConnection() e handleClientRead() WebServ.cpp
void WebServ::handleClientRead(int clientFd)
Passo a passo completo
1. recv() — lê até 65536 bytes. 0 → cliente fechou a conexão → removeClient(). Negativo → erro no socket (ex: conexão resetada pelo peer) → também removeClient(). Positivo → client->appendRequest(buffer, bytesRead) + client->isRequestComplete().

2. isRequestTooLarge() — verifica limite do body. Se exceder → 413 + POLLOUT.
WebServ.cpp — handleClientRead() — detecção de CGI e setup dos pipes
if (res.needsCgiExec()) {
    CgiProcess proc = CgiHandler::startCgi(...);
    if (!proc.valid) { /* 500 */ return; }
    // copia estado do proc para o Client
    client->cgiRunning   = true;
    client->cgiPid      = proc.pid;
    client->cgiPipeOut  = proc.pipeOut; // só pipeOut — body vai ao CGI via arquivo
    client->cgiTmpFd    = proc.tmpFd;
    client->cgiStartTime = time(NULL);
    // registra o pipeOut no poll — único pipe monitorado
    cgiPipeToClient[client->cgiPipeOut] = clientFd;
    addPollFd(client->cgiPipeOut, POLLIN);
}
Sem pipeIn, sem handleCgiWrite(). O body da requisição foi gravado em disco pelo Client durante o recv() (no arquivo reqTmpPath). O CgiHandler::startCgi() abre esse arquivo no filho e faz dup2(bodyFd, STDIN_FILENO) antes do execve() — o processo CGI lê o body diretamente do arquivo, sem que o pai precise enviar nada via pipe. Isso elimina toda a lógica de POLLOUT/pipeIn e simplifica o loop.
08 WebServ — o CGI assíncrono: Read e Finish WebServ.cpp
void WebServ::handleCgiRead(int pipeFd)
Lê a saída do CGI e acumula no arquivo temporário
Chamada quando poll() indica POLLIN (ou POLLHUP/POLLERR) no pipeOut do CGI. Lê até 64KB: read(pipeFd, buffer, 65536). Se positivo → write(client->cgiTmpFd, buffer, bytesRead) e incrementa cgiTotalOutput. Se zero ou negativo (EOF ou erro — CGI terminou) → fecha o pipe, remove do mapa e pollfds, chama finishCgi(clientFd).
09 WebServ — handleClientWrite() e removeClient() WebServ.cpp
void WebServ::removeClient(int clientFd)
Limpeza completa e garantida
É o único ponto de saída para um cliente — não importa o motivo (resposta enviada, erro, desconexão, timeout). Realiza em ordem:
1. Encontra o Client no map (guarda com find para evitar acesso duplo).
2. Se cgiPipeIn >= 0: remove do cgiPipeToClient e pollfds.
3. Se cgiPipeOut >= 0: idem.
4. Se cgiPid > 0: kill(SIGKILL) + waitpid(0) bloqueante — garante que o processo filho não fica zombie.
5. delete client — destrói o objeto (destrutor fecha fds, deleta tmp).
6. clients.erase(it) — remove do map.
7. removePollFd(clientFd) — remove do array.
8. close(clientFd) — fecha o socket TCP.
A ordem importa: delete client antes de clients.erase() e close(clientFd). O destrutor usa atributos do Client (cgiPipeIn etc.) — deve rodar enquanto o objeto ainda existe. O clients.erase(it) invalida o iterador mas o fd ainda está aberto — close(clientFd) fecha o socket por último. Se feito fora de ordem: UB ou fd leak.
waitpid() bloqueante nos três pontos de coleta de CGI: no timeout (run()), em finishCgi() e em removeClient(), todos usam waitpid(pid, &status, 0) sem WNOHANG. Funciona sem travar o loop porque cada chamada acontece num momento em que o processo já está terminando: no timeout, imediatamente após o kill(SIGKILL); em finishCgi(), depois que o pipe de saída já sinalizou EOF/erro; em removeClient(), também depois de um kill(SIGKILL). Em qualquer um desses três casos a espera é resolvida pelo kernel quase instantaneamente.
void WebServ::setPollEvent    void WebServ::addPollFd    void WebServ::removePollFd
Gestão do array pollfds
addPollFd(fd, events) — cria um struct pollfd, seta fd/events/revents=0, faz push_back.
removePollFd(fd) — busca por fd, chama pollfds.erase(it). O erase em vector é O(n) e realoca — mas o número de fds simultâneos é pequeno (< 1000) então não é problema.
setPollEvent(fd, event) — busca o fd e substitui o campo events. Usado para mudar entre POLLIN e POLLOUT para o mesmo fd — ex: quando a requisição chegou e precisamos enviar a resposta.
struct pollfd tem 3 campos: fd (o file descriptor), events (o que queremos monitorar — OR de POLLIN, POLLOUT, etc.), revents (o que aconteceu — preenchido pelo kernel após poll() retornar). Sempre zeramos revents na criação — é responsabilidade do kernel sobrescrever após poll().
