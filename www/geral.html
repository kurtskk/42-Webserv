00 Visão Geral — O que existe e quem faz o quê
🏗As 9 classes do projeto

Config → lê e valida o webserv.conf. Produz uma lista de ServerConfig.

ServerConfig → representa um bloco server {}. Guarda porta, nome, error_pages, client_max_body_size e uma lista de LocationConfig.

LocationConfig → representa um bloco location {}. Guarda root, index, métodos, CGI (ext+path), redirect, autoindex, upload_store, client_max_body_size.

WebServ → o motor. Tem o loop com poll(), aceita conexões, despacha leitura/escrita, gerencia CGI. Mantém o mapa de sessões.

Client → representa uma conexão aberta. Acumula headers no buffer e body em arquivo temporário (reqTmpFd). Guarda o estado da resposta e os fds do CGI.

HttpRequest → parse do texto cru da requisição (headers + request line). Produz método, URI, versão, headers.

HttpResponse → gera a resposta. Decide se é arquivo, redirect, CGI ou erro. Constrói o header HTTP. Implementa sessões.

CgiHandler → faz fork+execve. Alimenta o CGI com o body via arquivo tmp (stdin redirecionado). Lê saída via pipe. Monta variáveis de ambiente.

SocketUtils → helper estático. Cria socket TCP, faz bind/listen, seta O_NONBLOCK, aumenta SO_RCVBUF/SO_SNDBUF.

01 Startup — Do main() até o servidor estar ouvindo main.cpp → Config → WebServ
1️⃣main() — ponto de entradasrcs/main.cpp

Registra o handler de SIGINT (WebServ::signalHandler) que seta isRunning = false — o loop para limpo. Também ignora SIGPIPE (signal(SIGPIPE, SIG_IGN)) para não crashar ao escrever em socket fechado.

Valida que argc == 2. Cria Config, chama config.load(argv[1]). Cria WebServ com a config. Chama setupServers(). Chama run().

Tudo dentro de try/catch — qualquer exceção lançada no startup imprime o erro e retorna 1.

main()→ signal(SIGINT) + SIG_IGN(SIGPIPE)→ Config::load()→ WebServ::setupServers()→ WebServ::run()
2️⃣Config::load() — lê o arquivo de configuraçãosrcs/config/Config.cpp

Abre o arquivo com std::ifstream. Lê linha por linha. Para cada linha: remove comentários (stripComment), tokeniza (tokenize).

Quando encontra server { → chama parseServerBlock() que preenche um ServerConfig. Dentro do server block, quando encontra location /path { → chama parseLocationBlock() que preenche um LocationConfig.

O parser não impõe restrição sobre o número de porta — vários blocos server {} podem declarar o mesmo listen, o que é o que permite virtual hosting por nome (server_names diferentes compartilhando a mesma porta). O resultado é um vector<ServerConfig> com tudo preenchido.

Config::load()→ stripComment()→ tokenize()→ parseServerBlock()→ parseLocationBlock()
3️⃣WebServ::setupServers() — abre os sockets de listensrcs/server/WebServ.cpp

Itera sobre os ServerConfig. Para cada um chama SocketUtils::createListeningSocket(port).

Esse helper faz: socket() → setsockopt(SO_REUSEADDR) → aumenta SO_RCVBUF/SO_SNDBUF para 1MB → bind() → listen(SOMAXCONN) → setNonBlocking().

O fd retornado é salvo em serverSockets[listenFd] = port e adicionado ao array pollfds com evento POLLIN.

Tudo dentro de try/catch individual — se uma porta falhar, as outras continuam.

setupServers()→ SocketUtils::createListeningSocket()→ socket() bind() listen()→ setNonBlocking()→ addPollFd(listenFd, POLLIN)
O servidor usa O_NONBLOCK em todos os fds porque o poll() precisa saber quando o fd está pronto — se os fds fossem bloqueantes, um único recv() lento travaria todas as outras conexões. Com non-blocking, se não há dados o recv retorna imediatamente e o loop continua.
02 O Loop Principal — WebServ::run() srcs/server/WebServ.cpp
🔁O coração do servidor — while(isRunning)WebServ::run()

O loop tem três fases por iteração:

Fase 0 — Limpeza do pollfds: antes do poll(), remove entradas com fd == -1 (fds marcados como removidos pelos handlers anteriores).

Fase 1 — Timeout de CGI: itera sobre todos os clientes e verifica isCgiTimedOut(). Se ultrapassou 30s → mata o processo (kill(SIGKILL) + waitpid) → fecha pipes e tmp → prepara resposta 504 → coloca o fd do cliente em POLLOUT.

Fase 2 — Processar revents: itera sobre o array pollfds. Categoriza cada fd pronto em tipos e despacha para o handler correto. Não usa break — itera sobre todos os fds prontos de uma vez (o tamanho do loop é capturado antes em size_t size = pollfds.size()).

Sem break após handlers: o loop usa um índice fixo (size_t size = pollfds.size() capturado antes de iterar) e marca fds removidos com fd = -1 em vez de erase imediato — assim pode processar múltiplos fds prontos por iteração do while sem UB.
Sem handleCgiWrite: o body da requisição é escrito em arquivo temporário (reqTmpPath) pelo Client antes do CGI ser lançado. O processo filho recebe esse arquivo via stdin (dup2(bodyFd, STDIN_FILENO)). Não existe mais pipe de entrada para o CGI — apenas um pipe de saída (cgiPipeOut).
Só um poll() no loop inteiro porque o subject exige isso. O design de marcar fds com -1 em vez de erase imediato permite ao loop processar múltiplos eventos por ciclo sem invalidar iteradores.
03 Chegada de uma Requisição acceptNewConnection → handleClientRead → HttpRequest
🤝acceptNewConnection() — nova conexão TCPWebServ::acceptNewConnection()

Chama accept(serverFd, ...). Se retornar um fd válido: seta non-blocking com SocketUtils::setNonBlocking(), aumenta buffers do socket novo (1MB recv/send), cria new Client(clientFd, serverFd), salva em clients[clientFd], adiciona ao pollfds com POLLIN.

A partir desse momento o fd do novo cliente entra no loop e será processado nas próximas iterações.

acceptNewConnection()→ accept()→ setNonBlocking()→ new Client()→ addPollFd(clientFd, POLLIN)
📥handleClientRead() — dados chegandoWebServ::handleClientRead()

1. Chama recv(clientFd, buffer, 65536, 0). Se retornar 0 → cliente fechou → removeClient(). Se negativo com errno != EAGAIN → erro → removeClient().

2. Se dados chegaram: client->appendRequest(buffer, bytesRead) — acumula headers no requestBuffer e body em arquivo temporário (reqTmpFd).

3. Chama client->isRequestComplete() para verificar se já temos a requisição inteira.

4. Verifica tamanho: client->isRequestTooLarge(maxBody) — se passou do limite → resposta 413 → POLLOUT.

5. Verifica Expect: 100-continue — se isHeadersParsed() && getNeeds100Continue() && !getHasSent100Continue() e a requisição ainda não está completa → envia HTTP/1.1 100 Continue e seta sending100Continue = true.

6. Se a requisição está completa → constrói HttpRequest (a partir do requestBuffer que contém apenas os headers) → chama HttpResponse::generateResponse(req, server, sessions, reqTmpPath, reqBodyWritten). Passa o caminho do arquivo tmp com o body.

7. Se res.needsCgiExec() → chama CgiHandler::startCgi() passando o arquivo tmp do body como stdin do CGI. Registra cgiPipeOut no pollfds com POLLIN.

recv()→ appendRequest()→ isRequestComplete()→ isRequestTooLarge()→ HttpRequest(requestBuffer)→ generateResponse(reqTmpPath)
🔍Client::isRequestComplete() — quando parar de acumular?srcs/server/Client.cpp

Primeiro verifica se já encontrou \r\n\r\n (fim dos headers). Se não, ainda não temos nem os headers — retorna false.

Quando os headers chegaram (headersParsed = true): lê Content-Length e Transfer-Encoding: chunked. Se há body: abre um arquivo temporário (/tmp/webserv_req_PID_TIME_N) e escreve nele o body inicial que veio junto com os headers. Dados subsequentes de appendRequest() vão direto para esse arquivo — não ficam em memória.

Se Content-Length: requisição completa quando reqBodyWritten >= contentLength.

Se chunked: o parser processChunkedBody() decodifica os chunks em tempo real e escreve no arquivo tmp. Completo quando chunk de tamanho 0 é encontrado (requestComplete = true).

Se não há body: requisição completa ao receber os headers.

Detecta o header Expect: 100-continue → seta needs100Continue = true.

isRequestComplete()→ busca → \r\n\r\n→ abre → reqTmpFd→ escreve body → reqBodyWritten >= contentLength
📝HttpRequest — parse do texto crusrcs/http/HttpRequest.cpp

O construtor recebe a string crua completa. Divide em header part (antes do \r\n\r\n) e body.

Se for chunked: chama decodeChunkedBody() — um parser que lê tamanho em hex, extrai o chunk, até chegar em chunk de tamanho 0.

Se não for chunked: lê Content-Length e corta o body no tamanho exato.

parseRequestLine(): extrai método, URI, versão. Valida que o método é letras maiúsculas, URI começa com '/', versão começa com "HTTP/". Se qualquer coisa falhar → valid = false.

parseHeader(): para cada linha restante, encontra o ':' e separa chave → valor em um map<string, string>.

getCookie(name): lê o header Cookie e faz parse manualmente — divide por ';', encontra o par nome=valor desejado.

HttpRequest(raw)→ find \r\n\r\n→ decodeChunkedBody()ou substr(Content-Length)→ parseRequestLine()→ parseHeader() ×N
O Client acumula dados em vez de parsear na hora porque TCP pode fragmentar — a requisição pode chegar em vários pacotes. Só quando isRequestComplete() confirma que temos tudo é que construímos o HttpRequest. Assim garantimos que o parse sempre recebe dados completos.

🗺Longest-prefix matching — como encontra a location certa

Remove a barra final da URI de busca. Itera sobre todas as locations do ServerConfig. Para cada location: verifica se a URI começa com o path da location. Guarda a que tiver o path mais longo que casou.

Exemplo: URI /cgi-bin/hello.py → location / casa (1 char), location /cgi-bin/ casa (8 chars) → vence /cgi-bin/.

📂handleGet() — servindo arquivos e diretórios

Chama stat(targetFile). Se for diretório e autoindex == true: faz opendir() + readdir() e gera HTML com links. Se autoindex false e é diretório → 404.

Se for arquivo regular: seta isFileResponse = true, guarda o path e o tamanho. Determina Content-Type pela extensão (.css, .png, .jpg, default text/html).

Quando isFileResponse = true, o arquivo não é carregado na memória agora — só o header é gerado. O arquivo é servido em chunks de 64KB pelo Client::getResponseData() na fase de escrita.

handleGet()→ stat()→ dir? → opendir() readdir()ou arquivo → isFileResponse=true
📤handlePost() — upload de arquivos

Verifica se Content-Type é multipart/form-data. Extrai o boundary do header. Busca o boundary no body, pula para o \r\n\r\n do part header para chegar no conteúdo do arquivo. Extrai o filename do Content-Disposition do part.

Determina o upload_store da location (ou "upload_store" como default). Abre o arquivo com std::ofstream e escreve o conteúdo. Retorna 201 Created.

Se não for multipart → retorna 201 com o body cru no corpo da resposta (útil para testes com curl -d).

🗑handleDelete() — remoção de arquivo

Simplesmente chama unlink(targetFile). Se retornar 0 → 200 OK. Se falhar → 404 Not Found.

🔨buildResponseHeader() — construindo o header HTTP

Monta a string: HTTP/1.1 [statusCode] [statusMessage]\r\n + Content-Type + Content-Length + Location (se redirect) + Set-Cookie para cada cookie + Connection: close\r\n\r\n.

Se for fileResponse, Content-Length usa fileSize. Se não, usa body.length().

A decisão de CGI acontece em generateResponse() — ela apenas seta needsCgi=true e retorna string vazia. Quem de fato executa o CGI é o WebServ::handleClientRead() que chama CgiHandler::startCgi() logo depois. Separar "decidir" de "executar" mantém HttpResponse sem dependências de sistema (sem fork, sem pipes).
05 CGI — Fork, Pipes e Execve CgiHandler → WebServ → Client
⚙️O ciclo completo do CGI

O CGI tem 3 fases: 1) startCgi (fork+pipe — body já está em arquivo tmp), 2) leitura da saída do CGI via pipe (handleCgiRead → escreve em cgiTmpFd), 3) finishCgi (waitpid, parse do output CGI, envio ao cliente).

Não existe handleCgiWrite: o body da requisição foi acumulado em reqTmpPath pelo Client. O filho CGI o recebe via stdin (dup2 do arquivo).

🍴CgiHandler::startCgi() — o forksrcs/http/CgiHandler.cpp

Antes do fork: cria apenas um pipe (pipeOut[2] — saída do CGI). Chama buildEnvp() para montar as variáveis de ambiente. Cria arquivo temporário /tmp/webserv_cgi_PID_TIME_COUNTER para guardar a saída do CGI (proc.tmpFd).

Processo filho (pid==0): abre reqBodyPath (o arquivo tmp com o body da requisição) e faz dup2(bodyFd, STDIN_FILENO) — stdin vira o arquivo de body. dup2(pipeOut[1], STDOUT_FILENO) → stdout vira o pipe de saída. Fecha fds desnecessários. Monta argv = [cgiPath, scriptFile, NULL]. Chama execve(). Se execve falhar: escreve "Status: 500\r\n\r\n" no stdout e _exit(1).

Processo pai: fecha pipeOut[1] (ponta de escrita). Seta pipeOut[0] como non-blocking. Retorna a struct CgiProcess{valid, pid, pipeOut[0], tmpFd, tmpPath}. Não há pipe de entrada — sem handleCgiWrite.

pipe(pipeOut)→ buildEnvp()→ open(cgiTmpPath)→ fork()→ filho → dup2(bodyFile, STDIN) dup2(pipeOut[1], STDOUT) execve()
🌍buildEnvp() — variáveis de ambiente para o CGI

Monta: REQUEST_METHOD, SERVER_PROTOCOL, PATH_INFO, GATEWAY_INTERFACE, REDIRECT_STATUS, SERVER_NAME, SCRIPT_FILENAME, CONTENT_LENGTH, CONTENT_TYPE, QUERY_STRING (extraída da URI após '?').

Para cada header da requisição (exceto Content-Type, Content-Length, Transfer-Encoding) adiciona HTTP_NOME_HEADER=valor — traços viram underscores, lowercase vira uppercase.

💾handleCgiRead() → arquivo temporário → finishCgi()WebServ::handleCgiRead() + CgiHandler::finishCgi()

handleCgiRead(): lê do cgiPipeOut em chunks de 64KB e escreve no cgiTmpFd. Acumula o total em cgiTotalOutput. Quando o read retorna 0 ou negativo com errno != EAGAIN (CGI fechou o pipe) → remove pipe do cgiPipeToClient e pollfds → fecha pipe → chama finishCgi(clientFd).

WebServ::finishCgi(): faz waitpid bloqueante do processo CGI. Verifica se crashou: WIFSIGNALED(status) || (WIFEXITED && WEXITSTATUS != 0) — se crashou, responde 500. Senão, chama CgiHandler::finishCgi(cgiTmpFd, cgiTmpPath, cgiTotalOutput) que: fecha e reabre o tmp para leitura, lê os primeiros 8KB para encontrar os headers CGI (Status: e Content-Type:), calcula offset do body, retorna CgiResult.

Com o CgiResult: monta o header HTTP e chama client->setFileResponse(header, tmpPath, bodySize, offset, deleteOnClose=true). O tmp é deletado quando o Client é destruído.

Tanto o body da requisição quanto a saída do CGI vão para arquivos temporários em /tmp — nunca para memória. Isso suporta uploads e respostas grandes sem estourar RAM. O mesmo mecanismo de fileResponse serve arquivos estáticos, saídas de CGI e qualquer arquivo grande — reuso total de código.
06 Enviando a Resposta — handleClientWrite e Client WebServ::handleClientWrite → Client::getResponseData
📡handleClientWrite() — o remetenteWebServ::handleClientWrite()

Caso especial 100-Continue: se sending100Continue == true e a resposta terminou, reseta o estado e volta o fd para POLLIN — agora espera o body completo.

Caso normal: verifica getResponseRemaining(). Chama client->getResponseData(sendBuf, 65536) para preencher o buffer de envio. Chama send(clientFd, sendBuf, dataLen, 0). Se send retornar positivo → advanceResponseOffset(bytesSent). Se a resposta completou → removeClient(). Se send retornar negativo → removeClient().

handleClientWrite()→ getResponseRemaining()→ getResponseData(buf, 65536)→ send()→ advanceResponseOffset()→ completo → removeClient()
🗃Client — dois modos de respostasrcs/server/Client.cpp

Modo buffer (setResponse(string)): toda a resposta (header + body) está em responseBuffer. getResponseData() simplesmente copia a partir de responseSendOffset.

Modo arquivo (setFileResponse(header, path, size)): o header está em responseBuffer, o corpo está no arquivo em disco. getResponseData() primeiro esvazia o buffer do header, depois lê o arquivo em chunks de 64KB via responseFileFd. Isso evita carregar arquivos grandes na memória.

08 Por Que Decisões — Resumo das Escolhas de Design
🤔poll() em vez de select() ou epoll()

poll() foi escolhido por ser portável (Linux e macOS), mais simples que epoll (sem epoll_create/ctl/wait), e sem a limitação de 1024 fds do select FD_SET. O subject permite qualquer um — poll() é o meio-termo ideal para um projeto acadêmico.

🤔Arquivo temporário para saída do CGI

A saída do CGI pode ser grande. Guardar em memória (string) poderia estourar. O arquivo tmp em /tmp é criado com nome único (PID + time + contador) para evitar colisões entre múltiplos CGIs simultâneos. É deletado automaticamente no destrutor do Client. O mesmo mecanismo de fileResponse serve o tmp e arquivos estáticos — reuso.

🤔break após cada handler no loop

Handlers modificam o vetor pollfds (add/remove). Continuar iterando sobre um vetor modificado seria undefined behavior. O break reinicia o for na próxima iteração do while com um vetor consistente. Custo: só processa um fd pronto por iteração — mas o poll com timeout 1000ms garante que voltamos rapidamente e processamos os outros.

🤔Connection: close em todas as respostas

Keep-alive exigiria rastrear quando uma conexão está ociosa e reutilizá-la para múltiplas requisições — complexidade extra. Connection: close simplifica: cada requisição tem seu próprio ciclo de vida. O cliente sempre sabe que pode fechar a conexão após receber a resposta. Para o siege, o overhead de reconectar é pequeno comparado ao custo de implementar keep-alive corretamente.

🤔Sessions em memória (map no WebServ)

Para o bônus de cookies/sessão, um map em memória (sessions em WebServ) é a solução mais simples. A referência é passada para generateResponse(). Desvantagem: as sessões somem se o servidor reinicia. Mas para demonstrar o bônus é suficiente — e é exatamente o que o subject pede ("forneça exemplos simples").

🤔Por que HttpResponse seta needsCgi e não executa o CGI

HttpResponse não tem acesso ao pollfds, ao map de clients, nem ao cgiPipeToClient. Misturar lógica de rede com geração de resposta HTTP quebraria a separação de responsabilidades. O WebServ lê o flag needsCgi e toma a ação correta — quem sabe de rede é o WebServ, quem sabe de HTTP é o HttpResponse.
