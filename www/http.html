// O que este módulo faz e quem são suas 3 classes

HttpRequest — recebe o texto cru da requisição HTTP (já completo, acumulado pelo Client) e o parseia em estrutura de dados: método, URI, versão, headers (map), body. É construído uma única vez por requisição e lido por HttpResponse e CgiHandler.

HttpResponse — recebe o HttpRequest e o ServerConfig, toma todas as decisões de roteamento (qual location casa, qual método, CGI ou arquivo, redirect) e gera a resposta. É o maior arquivo do módulo e o cérebro do servidor.

CgiHandler — classe utilitária estática. Não guarda estado. É chamada pelo WebServ quando HttpResponse sinaliza que uma requisição precisa de CGI. Faz fork+pipe+execve e depois parseia a saída do processo filho.

Fluxo: WebServ cria um HttpRequest, passa para HttpResponse::generateResponse(). Se needsCgi → WebServ chama CgiHandler::startCgi(). Quando CGI termina → WebServ chama CgiHandler::finishCgi().

01 HttpRequest — o construtor e o parse do body HttpRequest.cpp
HttpRequest(const std::string &rawData)
Recebe de quem / quando
Chamado em WebServ::handleClientRead() quando client->isRequestComplete() retorna true. Recebe a string crua completa — headers + body — já acumulada no requestBuffer do Client. A partir desse momento o Client não precisa mais do buffer de rede, só da estrutura parseada.
Primeira decisão — separar headers do body
Busca \r\n\r\n com rawData.find(). Esse é o separador definido pelo RFC HTTP — uma linha em branco entre os headers e o body. Tudo antes é headerPart, tudo depois é rawBody. Se não encontrar \r\n\r\n, trata tudo como header (requisição sem body).
Segunda decisão — como tratar o rawBody
Verifica se o headerPart contém Transfer-Encoding: chunked (case-insensitive — testa dois casos). Se sim → body = decodeChunkedBody(rawBody). Se não → procura Content-Length (também case-insensitive, três variantes) e corta o rawBody no tamanho exato. Isso é necessário porque o TCP pode ter entregue bytes a mais ao final do buffer.
Terceira decisão — parsear o headerPart linha a linha
Cria um istringstream sobre o headerPart. Lê a primeira linha com getline → parseRequestLine(). Lê cada linha seguinte → parseHeader(). Antes de passar para cada parser, remove o \r do final da linha se existir — porque getline para no \n mas deixa o \r que precede ele no HTTP.
HttpRequest.cpp — construtor — estrutura principal
size_t headerEnd = rawData.find("\r\n\r\n");
std::string headerPart;
if (headerEnd != std::string::npos) {
    headerPart = rawData.substr(0, headerEnd);
    std::string rawBody = rawData.substr(headerEnd + 4); // +4 pula os 4 chars de \r\n\r\n

    bool isChunked = (headerPart.find("Transfer-Encoding: chunked") != std::string::npos)
                 || (headerPart.find("transfer-encoding: chunked") != std::string::npos);
    if (isChunked)
        body = decodeChunkedBody(rawBody);
    else {
        // extrai Content-Length com trim de espaços
        if (contentLength > 0 && contentLength <= rawBody.length())
            body = rawBody.substr(0, contentLength);
        else
            body = rawBody; // sem Content-Length: usa o rawBody inteiro
    }
}
else
    headerPart = rawData; // sem \r\n\r\n: tudo é header, body é ""

// parseia linha a linha via istringstream
std::istringstream stream(headerPart);
std::string line;
if (std::getline(stream, line)) {
    if (!line.empty() && line[line.length() - 1] == '\r')
        line.erase(line.length() - 1); // remove o \r antes do \n
    parseRequestLine(line);
}
while (std::getline(stream, line)) {
    if (!line.empty() && line[line.length() - 1] == '\r')
        line.erase(line.length() - 1);
    parseHeader(line);
}
Por que rawData.substr(headerEnd + 4)? — headerEnd é a posição do primeiro \r de \r\n\r\n. Esses 4 bytes (\r\n\r\n) são o separador e não pertencem nem ao header nem ao body. Pular exatamente 4 posiciona o cursor no primeiro byte do body.
Remoção do \r final: o HTTP usa \r\n como terminador de linha. std::getline quebra no \n mas deixa o \r na string. Sem a remoção, cada header teria um \r no final: "Content-Type: text/html\r" — causaria falha no headers.find() mais tarde. O idioma line[line.length()-1] == '\r' é a verificação antes do erase.
Content-Length — 3 variantes de case: o código busca "Content-Length: ", "Content-length: " e "content-length: ". Isso porque o RFC HTTP diz que header names são case-insensitive, mas o servidor armazena exatamente como recebeu. Clientes diferentes podem usar cases diferentes.
02 HttpRequest — decodeChunkedBody() HttpRequest.cpp — função estática local
static std::string decodeChunkedBody(const std::string &raw)
O que é chunked transfer encoding
Quando o cliente não sabe o tamanho total do body antecipadamente, ele envia em "chunks". Cada chunk começa com o tamanho em hexadecimal numa linha, seguido pelo dado, seguido por \r\n. O body termina com um chunk de tamanho 0. Exemplo: 5\r\nHello\r\n3\r\nbye\r\n0\r\n\r\n → "Hellobye".
O algoritmo — loop de desempacotamento
1. Encontra o fim da linha de tamanho com find("\r\n", pos).
2. Extrai a string hex (substr(pos, lineEnd - pos)). Remove extensões opcionais após ; (chunk extensions são raras mas RFC-válidas).
3. Converte hex para número com istringstream + std::hex. Se chunkSize == 0 → encerra o loop.
4. Avança pos para depois do \r\n, copia exatamente chunkSize bytes para decoded com append(raw, pos, chunkSize).
5. Avança pos sobre o dado + o \r\n que vem depois do chunk.
HttpRequest.cpp — decodeChunkedBody()
std::string decoded;
size_t pos = 0;
while (pos < raw.length()) {
    size_t lineEnd = raw.find("\r\n", pos);
    if (lineEnd == std::string::npos) break; // dado incompleto

    std::string hexSize = raw.substr(pos, lineEnd - pos);
    size_t semiPos = hexSize.find(';');
    if (semiPos != std::string::npos)
        hexSize = hexSize.substr(0, semiPos); // remove chunk extensions

    std::istringstream hexStream(hexSize);
    unsigned long chunkSize;
    if (!(hexStream >> std::hex >> chunkSize) || !hexStream.eof()) break; // hex inválido
    if (chunkSize == 0) break;                           // chunk final

    pos = lineEnd + 2;                                  // pula o \r\n do tamanho
    if (pos + chunkSize > raw.length()) break;          // dado incompleto
    decoded.append(raw, pos, chunkSize);               // copia o chunk
    pos += chunkSize;
    if (pos + 2 <= raw.length()) pos += 2;             // pula o \r\n após o dado
}
return (decoded);
hexStream >> std::hex >> chunkSize — std::hex é um manipulador de stream que instrui o operador >> a interpretar o próximo número como hexadecimal. Sem ele, "a" seria interpretado como falha de parse. Com ele, "a" = 10, "ff" = 255. O hexStream.eof() verifica que todo o string foi consumido — garante que "5x" (hex parcialmente inválido) seria rejeitado.
decoded.append(raw, pos, chunkSize) — versão de append que recebe (string_fonte, posição_início, quantidade). Mais eficiente que decoded += raw.substr(pos, chunkSize) porque não cria uma string temporária intermediária — copia diretamente do raw para decoded.
É uma função static livre (fora da classe, antes do construtor) em vez de membro. Isso a torna invisível fora do arquivo — static em funções livres em C++ (e C) tem o efeito de limitar o linkage ao arquivo de compilação. É uma forma de "função privada de arquivo" sem precisar declará-la no header.
03 HttpRequest — parseRequestLine() e parseHeader() HttpRequest.cpp
void HttpRequest::parseRequestLine(const std::string &line)
O que valida e por que a ordem importa
Lê os 3 tokens da request line: método, URI, versão. Depois tenta ler um 4º token — se conseguir, a linha tem tokens demais e é inválida. Depois valida cada campo individualmente. Só seta valid = true ao final, se tudo passou — é um padrão pessimista: assume inválido até provar o contrário.
HttpRequest.cpp — parseRequestLine()
std::istringstream stream(line);
std::string tempMethod, tempUri, tempVersion;
if (!(stream >> tempMethod >> tempUri >> tempVersion))
    return;                          // menos de 3 tokens → inválido
std::string extraToken;
if (stream >> extraToken)
    return;                          // mais de 3 tokens → inválido

// método: só letras maiúsculas (A-Z)
if (tempMethod.empty() || tempMethod.find_first_not_of("ABCDEFGHIJKLMNOPQRSTUVWXYZ") != std::string::npos)
    return;

// URI: deve começar com '/'
if (tempUri.empty() || tempUri[0] != '/')
    return;

// versão: deve começar com "HTTP/"
if (tempVersion.find("HTTP/") != 0)
    return;

method = tempMethod;
uri    = tempUri;
version = tempVersion;
valid  = true;  // só aqui → tudo válido
find_first_not_of("ABCDEFGHIJKLMNOPQRSTUVWXYZ") — retorna a posição do primeiro caractere que NÃO está no conjunto. Se retornar npos, todos os caracteres estão no conjunto — o método é pura maiúscula. É o idioma C++ para "string contém apenas estes caracteres".
tempVersion.find("HTTP/") != 0 — find() retorna a posição onde a substring foi encontrada. Se retornar 0, a string começa com "HTTP/". Se retornar qualquer outra coisa (incluindo npos), não começa com "HTTP/". Isso é mais explícito que tempVersion.substr(0,5) == "HTTP/" — sem criar substring temporária.
Variáveis temporárias (tempMethod, tempUri, tempVersion) antes de atribuir aos atributos. Isso garante atomicidade: ou todos os três são válidos e atribuídos, ou nenhum é. Sem temporárias, uma falha a meio do parse deixaria os atributos em estado inconsistente.
void HttpRequest::parseHeader(const std::string &line)
O que faz
Encontra o primeiro : na linha. Tudo antes é a chave, tudo depois é o valor (com trim de espaços/tabs no início). Insere em headers (map). Se não encontrar :, ignora a linha silenciosamente — linha vazia ou malformada não causa erro.
HttpRequest.cpp — parseHeader()
size_t colon = line.find(':');
if (colon != std::string::npos) {
    std::string key   = line.substr(0, colon);
    std::string value = line.substr(colon + 1);
    size_t start = value.find_first_not_of(" \t"); // trim espaços iniciais
    if (start != std::string::npos)
        value = value.substr(start);
    headers[key] = value; // insere ou sobrescreve no map
}
headers[key] = value no std::map tem comportamento de inserção-ou-substituição: se a chave já existe, sobrescreve; se não, insere. Para headers HTTP isso é adequado — se o cliente mandar dois Content-Type, o segundo vence. O map mantém as chaves em ordem alfabética (por ser uma BST internamente) — não importa para o servidor, mas é relevante saber.
04 HttpRequest — getCookie() HttpRequest.cpp
std::string HttpRequest::getCookie(const std::string &name) const
O formato do header Cookie
O browser envia todos os cookies em um único header: Cookie: session_id=abc123; user=joao; theme=dark. São pares nome=valor separados por ;. getCookie recebe o nome desejado e percorre esse header manualmente para encontrar o valor.
O algoritmo de busca
1. Busca o header "Cookie" no map. Se não existir → retorna "".
2. Loop: encontra o próximo ; para delimitar o cookie atual. substr(pos, semiPos - pos) extrai um par "nome=valor".
3. Encontra o = dentro do par. Divide em nome e valor. Aplica trim (find_first_not_of + find_last_not_of) no nome.
4. Se o nome casar com o procurado → retorna o valor. Avança pos para depois do ;.
HttpRequest.cpp — getCookie() — núcleo do loop
size_t pos = 0;
while (pos < cookieHeader.length()) {
    size_t semiPos = cookieHeader.find(';', pos);
    if (semiPos == std::string::npos)
        semiPos = cookieHeader.length(); // último cookie (sem ; no final)
    std::string cookie = cookieHeader.substr(pos, semiPos - pos);
    size_t eqPos = cookie.find('=');
    if (eqPos != std::string::npos) {
        std::string cookieName = cookie.substr(0, eqPos);
        // trim: remove espaços no inicio e fim do nome
        size_t start = cookieName.find_first_not_of(" \t");
        size_t end   = cookieName.find_last_not_of(" \t");
        if (start != std::string::npos)
            cookieName = cookieName.substr(start, end - start + 1);
        if (cookieName == name)
            return (cookie.substr(eqPos + 1)); // retorna o valor
    }
    pos = semiPos + 1; // avança para o próximo cookie
}
return ("");
find_last_not_of(" \t") — o par find_first_not_of + find_last_not_of é o idioma de trim bidirecional em C++98. O primeiro encontra onde o conteúdo real começa, o segundo onde termina. substr(start, end - start + 1) extrai só a parte não-espaço. O +1 no tamanho é necessário porque end é um índice (inclusivo) e substr espera um comprimento.
05 HttpResponse — generateResponse() — o dispatcher HttpResponse.cpp
std::string HttpResponse::generateResponse(const HttpRequest &req, const ServerConfig &serverConfig, std::map<std::string, std::map<std::string, std::string>> &sessions)
Recebe de quem / quando
Chamada em WebServ::handleClientRead() logo após construir o HttpRequest. Recebe o request parseado, o ServerConfig correspondente ao socket que aceitou a conexão, e uma referência ao mapa de sessões do WebServ (passado por referência porque pode ser modificado no login).
Etapa 0 — URIs especiais de sessão
Antes de qualquer roteamento, testa se a URI é /session_login ou /session_profile. Se for, processa e retorna imediatamente via buildResponseString(). Essas rotas são hardcoded — não passam pelo sistema de location matching. É uma decisão de implementação do bônus: simples e direta.
Etapa 1 — Longest-prefix matching das locations
Remove barra final da URI de busca (searchUri). Itera sobre todas as locations do ServerConfig. Para cada location, remove barra final do path também, verifica se searchUri começa com locPath E uma das três condições seguintes: a URI tem o mesmo tamanho que locPath (match exato), o próximo caractere é / (evita que /dir case com /directory), ou a própria location é a raiz / — que funciona como catch-all e deve casar com qualquer URI, já que toda URI HTTP começa com /. Guarda a location com o path mais longo que casou, então uma location mais específica como /uploads/ sempre vence sobre / quando ambas casam.
HttpResponse.cpp — generateResponse() — location matching
// remove barra final para comparação uniforme: "/uploads/" → "/uploads"
if (searchUri.length() > 1 && searchUri[searchUri.length() - 1] == '/')
    searchUri.erase(searchUri.length() - 1);

size_t longestMatch = 0;
for (size_t i = 0; i < locations.size(); ++i) {
    std::string locPath = locations[i].getPath();
    if (locPath.length() > 1 && locPath[locPath.length() - 1] == '/')
        locPath.erase(locPath.length() - 1);

    if (searchUri.find(locPath) == 0) {  // começa com locPath
        if (searchUri.length() == locPath.length() // match exato
            || searchUri[locPath.length()] == '/' // ou próximo char é /
            || locPath == "/") {              // ou a location é a raiz — catch-all
            if (locPath.length() > longestMatch) {
                longestMatch = locPath.length();
                matchedLoc = &locations[i];
            }
        }
    }
}
Etapa 2 — Checagens em cascata com early return
Após encontrar a location, cada verificação falha com return(buildResponseString()):
a) Nenhuma location casou → 404.
b) Location tem redirect → status 301/302 + Location header.
c) Método não permitido → 405. Tem uma exceção: se a location tem CGI e o método é POST, força methodAllowed = true mesmo que POST não esteja na lista — permite CGI POST mesmo em locations sem POST explícito.
d) Body excede maxBody → 413.
Etapa 3 — Construção do targetFile
Combina o root da location (ou do servidor) com a parte da URI após o path da location. Exemplo: URI /uploads/foto.jpg, location path /uploads/, root www/uploads → targetFile = www/uploads/foto.jpg.
Caso especial: se a URI bate exatamente no path da location (ex: URI /directory = location /directory/), usa o index da location diretamente. Depois um segundo stat() verifica se targetFile é diretório — se for, acrescenta o index.
Etapa 4 — CGI ou método handler
Se a extensão do targetFile bate com o cgi_ext da location → seta needsCgi = true, salva os paths e retorna "" (string vazia). O WebServ detecta o needsCgi e inicia o CGI. Se não for CGI → despacha para handleGet, handlePost ou handleDelete conforme o método.
Retorno "" no caso CGI é um contrato entre HttpResponse e WebServ. O WebServ em handleClientRead() faz: if (resp.needsCgiExec()) { startCgi(); return; }. A string vazia sinaliza que a resposta ainda não está pronta — será gerada pelo caminho do CGI. Qualquer outro retorno é tratado como resposta HTTP completa a ser enviada.
06 HttpResponse — handleGet, handlePost, handleDelete HttpResponse.cpp
void HttpResponse::handleGet(req, serverConfig, targetFile, matchedLoc)
Dois caminhos: diretório ou arquivo
Diretório: stat() confirma que é diretório (S_ISDIR). Se autoindex == true: abre com opendir(), itera com readdir(), gera HTML com links, fecha com closedir(). Se autoindex == false: retorna 404.

Arquivo regular: stat() confirma S_ISREG. Detecta Content-Type pela extensão (.css, .png, .jpg, default text/html). Seta isFileResponse = true, salva o filePath e fileSize = fileStat.st_size. O arquivo em si não é aberto aqui — será lido em chunks pelo Client durante o envio.
HttpResponse.cpp — handleGet() — autoindex e fileResponse
if (stat(targetFile.c_str(), &fileStat) == 0 && S_ISDIR(fileStat.st_mode)) {
    if (matchedLoc && matchedLoc->getAutoindex()) {
        DIR *dir = opendir(targetFile.c_str());
        if (!dir) { setErrorResponse(403, ...); return; }
        std::ostringstream page;
        struct dirent *entry;
        while ((entry = readdir(dir)) != NULL) {
            std::string name = entry->d_name;
            if (name == ".") continue;     // oculta "." mas mostra ".."
            page << "<a href=\"" << name << "\">" << name << "</a>\n";
        }
        closedir(dir);
        body = page.str();
    }
    else setErrorResponse(404, ...);
    return;
}
if (stat(targetFile.c_str(), &fileStat) == 0 && S_ISREG(fileStat.st_mode)) {
    // detecta Content-Type pela extensão
    isFileResponse = true;
    filePath = targetFile;
    fileSize = fileStat.st_size; // tamanho para o Content-Length
    statusCode = "200"; statusMessage = "OK";
}
else setErrorResponse(404, ...);
stat(path, &fileStat) — syscall POSIX que preenche um struct stat com metadados do arquivo (tamanho, tipo, permissões, timestamps). Retorna 0 em sucesso, -1 em erro. S_ISDIR(fileStat.st_mode) e S_ISREG(fileStat.st_mode) são macros que testam o campo st_mode. fileStat.st_size é o tamanho em bytes — usado como Content-Length.
isFileResponse = true em vez de ler o arquivo aqui: arquivos podem ser grandes (MB ou GB). Ler tudo em memória de uma vez seria impraticável. Com isFileResponse, o Client abre o arquivo depois e lê em chunks de 64KB por ciclo do poll(). O Content-Length ainda é correto porque usamos st_size do stat — sem precisar ler o conteúdo.
void HttpResponse::handlePost(req, serverConfig, targetFile, matchedLoc)
Parse de multipart/form-data — o upload de arquivo
Verifica Content-Type pelo header. Se for multipart/form-data: extrai o boundary ("boundary=" no header). O boundary delimita cada parte do multipart.
Encontra o boundary no body, pula para o \r\n\r\n do part-header para chegar no conteúdo binário real. Extrai o filename do Content-Disposition: form-data; name="file"; filename="foto.jpg". Encontra o fim do arquivo buscando o boundary novamente (recua 2 bytes para remover o \r\n antes do boundary). Abre um ofstream em modo binário e escreve com ofs.write().
HttpResponse.cpp — handlePost() — extração do arquivo
std::string boundary = "--" + it->second.substr(pos + 9); // "--" + valor após "boundary="

size_t fileStart = reqBody.find(boundary);
fileStart += boundary.length();
fileStart = reqBody.find("\r\n\r\n", fileStart); // pula os headers do part
fileStart += 4;                                     // pula o \r\n\r\n

size_t fileEnd = reqBody.find(boundary, fileStart); // próximo boundary = fim do arquivo
if (fileEnd >= 2) fileEnd -= 2;  // recua 2 para remover \r\n antes do boundary

std::ofstream ofs(savePath.c_str(), std::ios::out | std::ios::binary);
if (ofs) {
    ofs.write(reqBody.c_str() + fileStart, fileEnd - fileStart); // escrita binária direta
    statusCode = "201";
}
ofs.write(ptr, count) — escreve exatamente count bytes do ponteiro ptr sem interpretação. É a forma correta para dados binários — em contraste com ofs << que interpretaria bytes especiais (como \0 em strings C). reqBody.c_str() + fileStart é aritmética de ponteiro: obtém um const char* apontando para a posição exata do início do arquivo no buffer.
Se o Content-Type não for multipart: o servidor aceita o body cru como dados e retorna 201. Isso é útil para testes com curl -d "dados" — sem precisar montar um multipart completo.
void HttpResponse::handleDelete(req, serverConfig, targetFile)
O que faz — mais simples das 3
Chama unlink(targetFile.c_str()). unlink() é a syscall POSIX para remover um arquivo do sistema de arquivos. Retorna 0 em sucesso → 200 OK. Retorna -1 em falha (arquivo não existe, permissão negada) → 404 Not Found. Não distingue permissão de inexistência — ambos viram 404.
07 HttpResponse — buildResponseHeader, setErrorResponse, sessões HttpResponse.cpp
std::string HttpResponse::buildResponseHeader() const
Constrói o header HTTP completo
Usa std::ostringstream para concatenar o header de forma eficiente. Determina bodyLen: se isFileResponse usa fileSize (do stat), senão usa body.length(). Adiciona Location: apenas se for 301/302 e redirectUrl não for vazio. Itera o vector cookies e adiciona um Set-Cookie: por linha. Sempre termina com Connection: close\r\n\r\n.
HttpResponse.cpp — buildResponseHeader()
std::ostringstream response;
size_t bodyLen = isFileResponse ? fileSize : body.length();
response << "HTTP/1.1 " << statusCode << " " << statusMessage << "\r\n";
response << "Content-Type: "   << contentType << "\r\n";
response << "Content-Length: " << bodyLen      << "\r\n";
if ((statusCode == "301" || statusCode == "302") && !redirectUrl.empty())
    response << "Location: " << redirectUrl << "\r\n";
for (size_t i = 0; i < cookies.size(); ++i)
    response << "Set-Cookie: " << cookies[i] << "\r\n";
response << "Connection: close\r\n";
response << "\r\n"; // linha em branco que separa header do body
return (response.str());
std::ostringstream é um string builder. O operador << concatena ao buffer interno. .str() extrai a string final. É preferível a string += repetido porque o ostringstream gerencia o buffer de forma mais eficiente — faz menos realocações. Também permite inserir tipos não-string (int, size_t) diretamente sem conversão manual.
void HttpResponse::setErrorResponse(int code, const ServerConfig *srv = NULL)
Por que recebe um ponteiro e não referência
Ponteiro permite o valor NULL (argumento default). Quando chamado sem ServerConfig (ex: dentro de handlePost para erro de diretório), não precisa de srv. Com referência seria obrigatório passar um objeto válido. O código verifica if (srv) antes de usar — padrão "ponteiro opcional" em C++98.
Busca página de erro customizada
Se srv != NULL: busca o código em srv->getErrorPages() (map). Se encontrar, chama loadErrorPage(path, root) que abre o arquivo e retorna o conteúdo. Se o arquivo existir e não for vazio → usa como body. Se falhar qualquer coisa → fallback para o HTML embutido <h1>404 Not Found</h1>.
const std::string &HttpResponse::getSessionData(...) const
Por que retorna referência para string estática
Quando a sessão ou a chave não existem, a função precisa retornar algo. Não pode retornar uma string temporária por referência — ela seria destruída ao sair da função. A solução é uma static std::string emptyStr = "": ela existe durante toda a vida do programa. Retornar emptyStr por referência é seguro. É um padrão comum em C++98 para "retorna referência ou string vazia sem copiar".
HttpResponse.cpp — getSessionData()
static std::string emptyStr = ""; // existe para sempre — pode retornar referência
std::map<...>::const_iterator it = sessions.find(sessionId);
if (it == sessions.end())
    return (emptyStr); // sessão não existe
std::map<...>::const_iterator dataIt = it->second.find(key);
if (dataIt == it->second.end())
    return (emptyStr); // chave não existe nessa sessão
return (dataIt->second); // retorna referência ao valor real no map
map::const_iterator — iterador que não permite modificar os valores. Necessário porque a função é const (não modifica o objeto) e o mapa de sessões é const. Em C++11 seria possível usar auto, mas em C++98 o tipo completo é necessário. it->second acessa o valor do par (mapa de mapa): it->first é o sessionId, it->second é o map<string,string> de dados da sessão.
08 CgiHandler — buildEnvp() e startCgi() CgiHandler.cpp
static void CgiHandler::buildEnvp(const HttpRequest &req, const std::string &scriptFile, std::vector<char*> &envp)
Por que envp é vector<char*> e não vector<string>
execve() espera char* argv[] e char* envp[] — arrays de ponteiros para strings C terminadas em \0. std::string não é compatível diretamente. A solução é alocar cada variável de ambiente como um char[] com new, copiar o conteúdo com strcpy, e empurrar o ponteiro no vector. O vector termina com NULL — obrigatório para execve().
O helper pushEnv
Função estática livre que aloca o char[], copia a string e empurra no vector. Retorna bool — se a alocação falhar (new retorna NULL em sistemas onde não lança exceção), retorna false e buildEnvp chama freeEnvp() para liberar tudo que foi alocado até ali.
Transformação dos headers HTTP em variáveis de ambiente
Para cada header do request (exceto Content-Type, Content-Length, Transfer-Encoding que já têm variáveis específicas): prefixo HTTP_ + nome do header em uppercase com traços (-) substituídos por underscores (_). Ex: header X-Custom-Auth: valor → env HTTP_X_CUSTOM_AUTH=valor. A transformação é feita caractere por caractere com aritmética de char: c - 'a' + 'A' converte minúscula para maiúscula.
CgiHandler.cpp — transformação de header para env
std::string envName = "HTTP_";
for (size_t i = 0; i < key.length(); ++i) {
    char c = key[i];
    if (c == '-')
        envName += '_';
    else if (c >= 'a' && c <= 'z')
        envName += (c - 'a' + 'A'); // lowercase → uppercase: 'a'=97, 'A'=65, diff=32
    else
        envName += c;
}
c - 'a' + 'A' — aritmética de caracteres. Em ASCII, 'a' = 97 e 'A' = 65. A diferença é sempre 32. Subtrair 'a' obtém a posição na letra do alfabeto (0-25), somar 'A' chega na maiúscula correspondente. Mais eficiente que toupper() pois evita a chamada de função — e em C++98 toupper() tem comportamento definido por locale, o que pode ser problemático.
CgiProcess CgiHandler::startCgi(cgiPath, scriptFile, req, loc)
Sequência completa antes do fork
1. Cria dois pipes: pipeIn[2] (servidor → CGI, stdin do CGI) e pipeOut[2] (CGI → servidor, stdout do CGI).
2. Chama buildEnvp() para montar o array de ambiente.
3. Cria o arquivo temporário com nome único: /tmp/webserv_cgi_PID_TIME_COUNTER. Usa um static unsigned int tmpCounter para garantir unicidade mesmo com múltiplos CGIs no mesmo segundo. Abre com O_RDWR | O_CREAT | O_EXCL — O_EXCL garante que falha se o arquivo já existir (proteção contra race condition).
O processo filho (pid == 0)
Fecha as pontas do pipe que não usa. dup2(pipeIn[0], STDIN_FILENO) — o stdin do filho passa a ser a ponta de leitura do pipeIn. dup2(pipeOut[1], STDOUT_FILENO) — o stdout do filho passa a ser a ponta de escrita do pipeOut. Fecha os fds originais (não precisam mais deles — estão duplicados). Chama execve() com o interpretador e o script. Se execve falhar → escreve "Status: 500\r\n\r\n" no stdout (que agora é o pipe) e chama _exit(1).
CgiHandler.cpp — startCgi() — processo filho
if (pid == 0) {                        // FILHO
    close(pipeIn[1]);                   // fecha a ponta de escrita do pipeIn (é do pai)
    close(pipeOut[0]);                  // fecha a ponta de leitura do pipeOut (é do pai)
    dup2(pipeIn[0],  STDIN_FILENO);    // stdin = leitura do pipeIn
    dup2(pipeOut[1], STDOUT_FILENO);   // stdout = escrita do pipeOut
    close(pipeIn[0]);                   // fecha fd original (dup2 criou cópia)
    close(pipeOut[1]);
    char *argv[] = { arg0, arg1, NULL }; // ["/usr/bin/python3", "script.py", NULL]
    execve(cgiPath.c_str(), argv, &envp[0]);
    write(STDOUT_FILENO, "Status: 500\r\n\r\n", 15); // execve falhou
    _exit(1);                             // _exit: não chama destructors C++
}
O processo pai — o que faz após o fork
Fecha as pontas do pipe que são do filho (pipeIn[0], pipeOut[1]). Libera o envp (freeEnvp()) — no filho o execve já substituiu o processo, no pai não é mais necessário. Seta pipeIn[1] e pipeOut[0] como non-blocking com fcntl(fd, F_SETFL, O_NONBLOCK). Preenche e retorna a struct CgiProcess com valid=true.
dup2(oldfd, newfd) — duplica oldfd para o número newfd. Se newfd já estava aberto, fecha-o primeiro. Após dup2(pipeIn[0], STDIN_FILENO), tanto pipeIn[0] quanto STDIN_FILENO(0) apontam para a mesma ponta do pipe. O close(pipeIn[0]) depois remove o fd original, deixando só o STDIN_FILENO — que é o que o execve usa.
_exit(1) vs exit(1) — exit() chama os destructors de objetos estáticos, flush dos buffers e handlers registrados com atexit(). No processo filho após fork, isso poderia fechar fds que o pai ainda usa ou dar flush duplo. _exit() termina imediatamente sem nada disso — é o correto em processos filhos após fork.
O_CREAT | O_EXCL — combinação que cria o arquivo e falha se já existir. Sem O_EXCL, O_CREAT silenciosamente abriria um arquivo existente. Com O_EXCL, é atômico: criação e verificação de unicidade numa única syscall, sem race condition.
09 CgiHandler — finishCgi() e parseCgiHeaders() CgiHandler.cpp
CgiResult CgiHandler::finishCgi(int tmpFd, const char* tmpPath, size_t totalOutput)
Recebe de quem / quando
Chamada por WebServ::finishCgi(clientFd) quando o pipe de saída do CGI fecha (leitura retorna 0 ou negativo em handleCgiRead()). Recebe o fd do arquivo temporário (aberto para escrita), o path do mesmo arquivo e o total de bytes escritos nele.
Por que fecha e reabre o tmpFd
O tmpFd foi aberto em modo O_RDWR e estava sendo usado para escrita (write(tmpFd, ...) em handleCgiRead()). O cursor de arquivo está no final. Para ler do início, seria possível usar lseek(tmpFd, 0, SEEK_SET). O código opta por fechar e reabrir em O_RDONLY — mais explícito e sem ambiguidade sobre a posição do cursor.
Estratégia de leitura dos headers CGI
Lê os primeiros 8192 bytes do arquivo em headerBuf. Busca \r\n\r\n (e fallback para \n\n porque alguns CGIs usam só \n). Esse separador divide os headers CGI do body. Chama parseCgiHeaders() para extrair Status e Content-Type. Calcula bodyOffset = posição após o separador. Calcula bodySize = totalOutput - bodyOffset.
CgiHandler.cpp — finishCgi() — cálculo do offset
size_t headerEnd = headerChunk.find("\r\n\r\n");
size_t headerSepLen = 4;
if (headerEnd == std::string::npos) {
    headerEnd = headerChunk.find("\n\n");
    headerSepLen = 2;                   // CGI usa só \n (Unix puro)
}
size_t bodyOffset = 0;
if (headerEnd != std::string::npos) {
    parseCgiHeaders(...);
    bodyOffset = headerEnd + headerSepLen; // início do body no arquivo
}
result.bodySize = totalOutput > bodyOffset ? totalOutput - bodyOffset : 0;
result.fileStartOffset = bodyOffset; // o Client vai lseek para cá antes de ler
result.useFile = true;
result.tmpFilePath = tmpPath;
O que o WebServ faz com o CgiResult
Usa result.statusCode e result.contentType para chamar client->setFileResponse(header, tmpFilePath, bodySize) com fileStartOffset. O Client abre o tmpFile, faz lseek(fd, fileStartOffset, SEEK_SET) para pular os headers CGI e começa a ler o body a partir daí. O arquivo temporário é deletado no destrutor do Client com unlink(tmpPath).
static void parseCgiHeaders(headerChunk, headerEnd, statusCode, statusMessage, contentType)
O que parseia
Extrai apenas dois campos dos headers CGI: Status: e Content-Type:. O Status: tem o formato Status: 200 OK — divide pelo primeiro espaço para separar code de message. Suporta CGIs que usam \n simples ou \r\n detectando qual separador de linha está presente. Se não encontrar Status:, mantém os defaults "200 OK". Antes de retornar, normaliza os três campos extraídos removendo qualquer \r ou \n residual do final do valor — proteção contra scripts CGI que não fecham os headers exatamente com a sequência de separador esperada.
static void CgiHandler::freeEnvp(std::vector<char*> &envp)
Por que é necessário e como funciona
Cada entrada do envp foi alocada com new char[]. Após o execve() no filho, o sistema libera toda a memória do processo. No pai, depois de chamar fork, o envp não é mais necessário — deve ser liberado. Se o fork falhar, deve ser liberado na hora. Se o buildEnvp falhar a meio, libera o que já foi alocado. Itera o vector e chama delete[] em cada ponteiro não-nulo, depois faz clear().
O NULL que termina o envp é empurrado diretamente como envp.push_back(NULL) — não é alocado com new. Por isso o loop faz if (envp[i]) antes de deletar — o NULL do final seria deletado de um endereço nulo, causando undefined behavior.
